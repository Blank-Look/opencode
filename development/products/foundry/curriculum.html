Module 1 ~30 min — self-paced

Why GitHub?

Why not SharePoint? Git vs GitHub. Repositories, Markdown, Pull Requests, GitHub Actions, AI integration.

Learning objectives

✓ Explain the difference between Git and GitHub
✓ Identify why GitHub is better than SharePoint for code and docs
✓ Name the core GitHub features: repos, PRs, Actions, Issues
✓ Understand how AI tools integrate with GitHub

Content

  • Why not SharePoint? Version history is per-file, no branching, no review workflow, no automation. GitHub treats everything as code — docs, config, scripts.
  • Git vs GitHub: Git is the version control engine. GitHub is the platform that hosts repos, adds collaboration features, and connects to AI tools.
  • Key concepts: Repository, commit, branch, pull request, merge, Actions, Issues, Markdown.
  • AI integration: ChatGPT can generate code and docs. Copilot completes inline. OpenCode/Claude Code build entire features from prompts. GitHub is the single source of truth they all work with.

Module 2 ~1 h — self-paced

Markdown

Headings, lists, tables, links, images, Mermaid diagrams, code blocks. Hands-on from the start.

Learning objectives

✓ Write Markdown with headings, lists, tables, links, and images
✓ Add code blocks with syntax highlighting
✓ Create a Mermaid diagram inline
✓ Write a README.md from scratch

Content

  • Headings: # through ###### — one # per document title.
  • Text: Bold (**text**), italic (*text*), strikethrough (~~text~~).
  • Lists: Unordered with -, ordered with 1..
  • Links: [text](url). Relative links for internal docs.
  • Images: ![alt](path).
  • Tables: Pipes and dashes. Align with :---, :---:, ---:.
  • Code blocks: Triple backticks with language for syntax highlighting (```powershell, ```yaml, ```bash).
  • Mermaid: Fenced code block with ```mermaid renders flowcharts, sequence diagrams, Gantt charts.
Exercise

Create a README.md for an Intune application packaging repository. Include a heading, description, table of supported apps, a PowerShell code block for the install command, and a Mermaid flowchart showing the packaging workflow.

Module 3 ~1.5 h — self-paced

Git Basics

Clone, status, add, commit, push, pull. Working copy → Commit → Repository → Remote.

Learning objectives

✓ Clone a repository from GitHub
✓ Check status and stage changes
✓ Commit changes with a descriptive message
✓ Push commits to GitHub and pull changes from others

Content

  • Clone: git clone <url> — downloads the entire repository to your machine.
  • Status: git status — shows changed, staged, and untracked files.
  • Stage: git add <file> or git add . — stages changes for commit.
  • Commit: git commit -m "message" — saves a snapshot with a message. Messages should be present tense, descriptive: "Add Intune app packaging guide" not "updated stuff".
  • Push: git push — sends commits to GitHub.
  • Pull: git pull — fetches and merges changes from GitHub.
  • Log: git log --oneline — shows commit history in compact form.
Exercise — Shared Repository

Clone the training repo. Create a markdown file, stage it, commit, and push. Then edit a file another person created and practice the push-pull cycle. To learn conflict resolution, try editing a file you know someone else is also editing — Git will show you how to resolve it when you pull.

Module 4 ~1.5 h — self-paced

Branches & Pull Requests

Create branch → Edit → Commit → Push → PR → Review → Merge. Including merge conflicts — everyone resolves one.

Learning objectives

✓ Create and switch between branches
✓ Push a branch and open a Pull Request
✓ Review a PR and leave comments
✓ Merge a PR and resolve a merge conflict

Content

  • Branch: git branch <name>, git switch <name>. A branch is a parallel version of the repository.
  • Pull Request: Proposes changes from a branch to main. Enables review, discussion, and automated checks before merging.
  • PR description: What changed, why, and how to test. Reference Issues with #.
  • Review: Comment on specific lines, approve, request changes. Reviewers are assigned in the PR.
  • Merge: Three types — merge commit, squash merge, rebase merge. Use squash merge for feature branches (clean history).
  • Conflict: When two branches edit the same line. Git marks the conflict in the file. You choose which version to keep.
Exercise — Cross-Team PR

Create a branch, edit a file, commit, push, and open a PR. Then review a PR from another person, leave a comment, and approve it. For conflict resolution: edit the same line in a file as someone else, then practice resolving the conflict when you merge.

Module 5 ~1 h — self-paced

Repository Standards

README, docs/, scripts/, .github/, LICENSE, CODEOWNERS. How to structure every repo consistently.

Learning objectives

✓ Structure a repository with a consistent directory layout
✓ Write a README.md that explains purpose, usage, and ownership
✓ Add a LICENSE file and CODEOWNERS
✓ Use .github/ for templates and workflows

Content

  • Standard layout: README.md, docs/, scripts/, .github/, LICENSE, .gitignore.
  • README.md: Project title, description, usage, install steps, owners, links to related repos. First thing people see.
  • LICENSE: Always include one. Internal repos use "UNLICENSED" or MIT. Templates are available.
  • CODEOWNERS: .github/CODEOWNERS — defines who auto-reviewers are for specific paths. Every repo needs at least one owner.
  • .gitignore: Prevents committing secrets, build artifacts, OS files, IDE config. Templates exist for every language.
  • Naming conventions: Lowercase with hyphens. intune-packaging, azure-lz-docs, not Intune Packaging V2 Final.
Exercise — Build a Repository

Each person creates a new repository from scratch (or uses a template). Add: README.md, docs/ folder with one page, .github/CODEOWNERS with themselves as owner, .gitignore for PowerShell projects, and a LICENSE file. Commit and push.

Module 6 ~1 h — self-paced

GitHub Actions

Just enough to understand. Push → workflow starts → tests → deploy docs. No deep YAML.

Learning objectives

✓ Explain what GitHub Actions does at a high level
✓ Read a basic workflow YAML file
✓ Trigger a workflow by pushing to a repository
✓ See workflow results in the Actions tab

Content

  • What is GitHub Actions? Automation triggered by events — push, PR, schedule, manual.
  • Workflow: A YAML file in .github/workflows/. Defines trigger, jobs, and steps.
  • Parts of a workflow: on: (trigger), jobs: (what to run), steps: (individual actions).
  • Use case for docs: Push Markdown → Action runs MkDocs → Site updates. No manual deploy.
  • Use case for CI: Push code → Action runs tests → Reports pass/fail on the PR.
  • Marketplace: Pre-built actions for common tasks — deploy to Azure, send Teams notification, lint Markdown.
Exercise — Docs Deploy

A workflow file is provided in the training repo. Participants push a markdown file change to a branch, open a PR, see the Action run, merge, and verify the documentation site updates automatically.

Module 7 ~1 h — self-paced

AI

ChatGPT, Copilot, OpenCode, Claude Code — generating documentation, writing PowerShell, reviewing PRs, and building workflows with AI.

Learning objectives

✓ Use ChatGPT to generate a README and improve existing Markdown
✓ Use Copilot inline completions in VS Code
✓ Use an AI coding agent (OpenCode/Claude Code) to write a script
✓ Review AI-generated code before committing

Content

  • ChatGPT for docs: Prompt: "Write a README.md for an Intune application packaging repository. Include a table of supported apps and install commands." Review, tweak, commit.
  • ChatGPT for PowerShell: Prompt: "Write a PowerShell script that exports all Intune device compliance policies to CSV." Generate, review, save.
  • Copilot: Inline code completion in VS Code. Start typing a comment or function name, Copilot suggests the rest.
  • OpenCode / Claude Code: Terminal-based agents. Describe what you want in a prompt, they build files, run commands, commit changes. Always review before accepting.
  • PR review with AI: Ask ChatGPT to review a Pull Request diff. It catches missing error handling, typos, and style issues.
  • Golden rule: AI generates. Humans approve. Never commit AI output without reading it first.
Hands-on stations (rotate every 15 min)

Station 1 — ChatGPT: Generate a README, improve it, generate a PowerShell script, ask it to explain a complex script from the repo.
Station 2 — Copilot: Open VS Code, start writing a function, see completions. Try comments that describe intent.
Station 3 — AI agent: Run OpenCode or Claude Code with a prompt to generate a simple workflow file.
Station 4 — PR review: Open a PR in the training repo, paste the diff into ChatGPT, ask for a review.

Module 8 ~30 min — self-paced

Engineering Standards

How your organisation will work. Repository naming, PRs, reviews, Issues, Projects, documentation, branch protection.

Learning objectives

✓ Agree on repository naming conventions for the team
✓ Define minimum PR requirements (description, reviewer, checks)
✓ Set up branch protection rules on main
✓ Decide how to use Issues and Projects for tracking work

Content

  • Repository naming: intune-packaging, azure-lz-docs, entra-id-scripts. Lowercase, hyphens, descriptive. Agree as a team and write it down.
  • PR requirements: Every PR needs a description. At least one reviewer. All checks must pass. No self-merge to main.
  • Branch protection: Enable on main: require PR, require approval, require status checks, dismiss stale reviews.
  • Issues: Use for tasks, bugs, enhancements. Labels: bug, enhancement, docs, question. Templates help consistency.
  • Projects: Kanban-style boards. Columns: To Do, In Progress, In Review, Done. Link Issues and PRs.
  • Documentation: Every repo must have a README.md. Engineering docs live in the repo, not SharePoint.
  • CODEOWNERS: Every repo has at least one owner. Critical paths (security, config) may require specific owners.
Team agreement

Define your team's conventions: naming rules, PR workflow, branch protection, Issue labels, and Project board columns. Document the decisions in an engineering-standards.md file and commit it to your team's standards repository.

Track 3

Module 10 ~45 min — self-paced

AI Development Governance

AGENTS.md as guardrails, role-based governance, deterministic risk rules, source system authority, Delivery Prompt lifecycle.

✓ Explain how AGENTS.md acts as guardrails for AI
✓ Distinguish role-based governance from individual-based
✓ Apply deterministic risk rules to AI-assisted tasks
✓ Map the Delivery Prompt Template phases to a product build

Content

  • AGENTS.md as guardrails: Read by every AI tool before starting work. Defines context, commands, conventions, and constraints. The contract between team and AI.
  • Role-based governance: Roles (owner, maintainer, contributor) in CODEOWNERS and AGENTS.md. Persists beyond individuals. AI never acts as final approver.
  • Deterministic risk rules: Clear, binary boundaries — no auto-commit, no secrets, no unrelated changes, no prod deploy without PR. Encoded in AGENTS.md and branch protection.
  • Source systems authoritative: AI reads and generates, never replaces source system data. Authoritative systems (AD, SharePoint, Intune) remain unchanged.
  • Delivery Prompt Template: Phase 0 (discovery) → Phase 1 (foundation) → Phase 2 (MVP) → Phase 3 (integrations) → Phase 4 (workflows) → Phase 5 (onboarding). Each phase has a definition of done.
  • AI dev workflow: Read AGENTS.md → describe task → AI generates → human reviews → commit via PR → role-authorised approval → audit trail.
Exercise — Map the Governance

Open the SchoolApp product directory (products/schoolapp/). Read its README.md and ADR-001. Ask OpenCode: "What governance rules apply to the SchoolApp product based on its AGENTS.md and ADRs?" — review the answer and discuss how the rules protect the development process.

Track 4

AI Prompt Engineering

Structure prompts so AI builds apps and products with minimal rework. Context, role, constraints, format.

Module 11 ~60 min — self-paced

AI Prompt Engineering

How to tell AI what to do effectively — prompt anatomy, role prompting, breaking products into pieces, precise iteration, and the Delivery Prompt pattern.

✓ Structure prompts with context, task, format, and constraints
✓ Use role prompting to improve output quality
✓ Break products into prompt-sized pieces to reduce rework
✓ Iterate with precision — know what to change and why
✓ Apply the Delivery Prompt pattern at product scale

Content

  • Prompt anatomy: Every prompt needs four elements — context (background the AI needs), task (what to do), format (how the output should look), constraints (boundaries and rules). Weak prompts generate rework; strong prompts ship faster.
  • Role prompting: Tell AI who it is before asking it to build. "You are a senior front-end developer building accessible mobile-first web apps. No frameworks." — the role sets the standard.
  • Small pieces: Instead of one giant prompt, break a product into focused prompts: shell → dashboard → subjects → timetable → links → polish. Each piece takes under a minute and produces complete, reviewable output.
  • Precise iteration: Don't say "that's not right." Say "keep everything but change the accent colour to amber and increase the schedule item padding to 1rem." Precision reduces rework.
  • Delivery Prompt pattern: The same structured approach scales from one file to a whole product — Phase 0 (discover) → Phase 1 (foundation) → Phase 2 (MVP) → Phase 3+ (integrations and polish).
  • Common pitfalls: Vague tasks, missing constraints, too much at once, no format specified, changing topic mid-conversation, not reviewing output, assuming AI remembers.
Exercise — Weak vs Strong

Ask an AI to "Create a student dashboard." Compare the output with a structured prompt: "Single HTML page showing today's class schedule (09:00-16:00), a row of quick-link icons for Blackboard/Canvas/Portal/M365, and a what's-on section with event cards. Mobile-first, Inter font. No frameworks." Then iterate with precision: "Keep everything, but change the accent colour to amber and expand quick links to 6 columns."
