How AI Tools Work Inside Your Governance Framework

AI-assisted development isn't unregulated. Every SchoolCode product operates within a governance framework that defines how tools are used, who owns what, and what boundaries the AI cannot cross. This module explains that framework and how AGENTS.md enforces it.

What you'll learn

  • How AGENTS.md acts as guardrails for AI behaviour
  • Role-based governance — authority follows roles, not individuals
  • Deterministic risk rules — predictable boundaries for AI
  • Source systems remain authoritative — AI is a layer, not the source
  • The Delivery Prompt Template lifecycle

AGENTS.md as guardrails

Every repository in this organisation has an AGENTS.md at its root. When AI tools like OpenCode or Claude Code start working, they read this file first. It tells them:

  • Project context — what this repo is, what it contains
  • Workflow commands — how to run tests, lint, build
  • Conventions — naming, structure, code style
  • Constraints — what the AI must not do (e.g. commit without review, touch specific files)

The AGENTS.md file is the contract between the development team and the AI. It ensures every AI interaction follows the same rules, regardless of which tool or model is used.

Exercise — Read the Guardrails

Open the AGENTS.md file at the repository root. Find the constraints section. Ask OpenCode: "What are the constraints listed in AGENTS.md?" — confirm it respects them.

Role-based governance

Governance in this framework is attached to roles, not named individuals. A repository has owners, maintainers, and contributors — defined in CODEOWNERS and AGENTS.md. When someone leaves, the role persists. AI tools read role assignments to determine who can approve what.

This means:

  • AI never acts as a final approver — humans with the right role approve changes
  • Role definitions are in the repo, not in someone's head
  • Onboarding a new person means adding them to a role, not rewriting process

Deterministic risk rules

Rather than relying on an AI model to "behave responsibly" (opaque and unpredictable), this framework uses deterministic risk rules — clear, binary boundaries that the AI cannot cross:

  • No auto-commit — AI generates, human approves and commits
  • No secret exposure — .gitignore rules are enforced, secrets never written to files
  • No unrelated changes — AI only touches files relevant to the task
  • No production deployment without PR — every change goes through review

These rules are encoded in AGENTS.md and enforced by tool configuration (opencode.json, branch protection). The AI doesn't decide what's safe — the framework does.

Source systems remain authoritative

AI tools are an aggregation layer, not a source of truth. The authoritative systems — Active Directory, SharePoint, Intune, the student portal — remain unchanged. AI reads from them, generates outputs, and writes to Git-tracked files. But the original system data is never replaced by AI output.

This principle means:

  • AI-generated documentation is a convenience copy, not the record of truth
  • AI cannot modify source systems directly — only through approved PRs with human review
  • Audit trails show what AI generated and what a human approved

The Delivery Prompt Template lifecycle

When building a new product or feature, the Delivery Prompt Template enforces structured delivery:

  • Phase 0 — Inspect the repo, produce architecture docs, assumptions, risks, and implementation plan before writing code
  • Phase 1 — Foundation — directory structure, config, basic shell
  • Phase 2 — Core MVP — minimal viable product with core features
  • Phase 3 — Integrations — connect to source systems
  • Phase 4 — Workflows — automated processes
  • Phase 5 — Onboarding — docs, templates, handover

The definition of done at every phase includes: acceptance criteria, validation, audit trail, safe logs, no secrets, migration planning, and testing. AI tools help execute each phase, but the governance framework defines what "done" means.

Exercise — Map the Governance

Open the SchoolApp product directory (products/schoolapp/). Read its AGENTS.md (if present), README.md, and ADR-001. Ask OpenCode: "What governance rules apply to the SchoolApp product based on its AGENTS.md and ADRs?"

How AI dev uses the tool within governance

An AI-assisted developer's workflow within this framework looks like this:

1. Read AGENTS.md — understand project context and constraints
2. Open a task — describe what needs to be built or changed
3. AI generates — reads files, writes code, suggests changes
4. Human reviews — check every line before staging
5. Commit via PR — all changes go through a pull request
6. Approve and merge — a role-authorised human approves
7. Audit trail — Git history shows what AI generated and who approved

The governance framework doesn't stop AI from being fast. It ensures AI stays within safe boundaries. Speed with guardrails is the goal — not speed without process.

Key takeaways

  • AGENTS.md is the contract — AI reads it before anything else
  • Roles, not individuals — governance persists when people change
  • Deterministic rules — clear boundaries beat opaque AI judgment
  • Source systems stay authoritative — AI is an aggregation layer
  • Delivery phases — build in vertical slices, each with a clear definition of done
  • AI generates, humans approve — every change goes through review
