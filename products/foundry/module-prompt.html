How to Tell AI What to Do

The difference between getting what you want on the first try and spending hours iterating comes down to one skill: prompt engineering. This module teaches you how to structure prompts so AI builds apps and products with minimal rework — the same structured approach used across every SchoolCode product.

What you'll learn

  • Structure a prompt so AI delivers the right output first time
  • Use context, constraints, and format to reduce rework
  • Break a product into small, promptable pieces
  • Iterate with precision — know what to change and why

The anatomy of an effective prompt

Every prompt should include four elements:

ElementPurposeExample
ContextWhat the AI needs to know before it can answer"You are building a student hub for master's students."
TaskWhat you want it to do"Create a timetable page that shows weekly classes."
FormatHow the output should look"Single HTML file with inline CSS. Mobile-first."
ConstraintsWhat it must not do or must stay within"No external dependencies. No JavaScript frameworks."

A weak prompt says: "Build me a student app." A strong prompt says: "Build a student hub dashboard showing today's schedule, quick links to Blackboard and Canvas, and upcoming events. Single HTML file. Mobile-first. No external dependencies." The strong prompt gets you 90% of the way there. The weak prompt starts a conversation that takes ten rounds.

Exercise — Weak vs Strong

Open an AI chat or OpenCode. First, give it: "Create a student dashboard." See what you get. Then try: "Single HTML page showing today's class schedule (09:00-16:00), a row of quick-link icons for Blackboard/Canvas/Portal/M365, and a what's-on section with event cards. Mobile-first, Inter font. No frameworks." Compare the results.

Role prompting — tell AI who it is

Before asking AI to build something, tell it what role to play. This dramatically improves output quality because the AI selects relevant patterns and vocabulary:

"You are a senior front-end developer who builds accessible, mobile-first web apps.
No frameworks, no build tools. Just clean HTML, CSS, and vanilla JS."

Role prompting works for any domain — security reviewer, PowerShell scripter, infrastructure architect, documentation writer. The role tells the AI what standards to apply.

Break products into prompt-sized pieces

The biggest cause of rework is asking for too much in one prompt. Instead of "Build me a student app", break it down:

PiecePrompt focusOutput
1. ShellHTML structure, navigation, empty sectionsApp shell with tabs
2. DashboardSchedule layout, quick links, event cardsDashboard content
3. SubjectsCourse grid with progress barsSubjects page
4. TimetableWeekly grid with day headersTimetable page
5. LinksApp launcher grid with iconsLinks page
6. PolishColours, spacing, responsive breakpointsFinal styling

Each piece is a focused prompt. The AI delivers something complete in under a minute. You review, accept or tweak, and move to the next piece. Total time for a full app shell with content: under an hour.

How to iterate without starting over

When the output isn't right, don't start a new conversation. Tell the AI what to change:

  • Bad: "That's not what I wanted." (AI has to guess)
  • Good: "The schedule items should include the room number. Add a subtitle under each event card showing the location and time." (AI knows exactly what to fix)
  • Better: "Keep everything else, but change the quick links row from 4 columns to 6 columns on desktop." (Precise, no collateral damage)

The key insight: AI has no memory of what you meant — only what you said. The more precise your iteration instruction, the less rework you create.

Exercise — Iterate with Precision

Take the output from the previous exercise. Now give the AI this: "Keep everything as is, but change the accent colour from the default blue to a warm amber (#B45309). Update all button colours, link colours, and the selected tab indicator. Do not change anything else." See how precisely it follows the instruction vs a vague "make it amber".

The Delivery Prompt pattern

The Delivery Prompt Template used across SchoolCode products is itself a prompt-engineering pattern. It structures AI interaction by phase:

  • Phase 0 — Discover: "Inspect this codebase and produce architecture docs, assumptions, risks, and an implementation plan."
  • Phase 1 — Foundation: "Create the directory structure, config files, and basic entry point following the patterns in existing products."
  • Phase 2 — MVP: "Build the core feature set: [list features]. Match the conventions seen in [existing file]."
  • Phase 3+: Each subsequent phase is its own focused prompt with a clear definition of done.

This is prompt engineering applied at the product level: small, focussed pieces, each with context, task, format, and constraints.

Common pitfalls and how to avoid them

PitfallResultFix
Vague taskAI writes a novel instead of codeBe specific about output type
Missing constraintsAI uses React when you said no frameworksAdd "No frameworks. No build tools. Single file."
Too much at onceAI misses half the requirementsBreak into smaller prompts
No format specifiedAI returns markdown when you need HTMLSay "Single HTML file with inline CSS and JS."
Changing topic mid-conversationAI confuses old context with new requestStart a fresh prompt for each new task
Not reviewing outputBugs, security issues, wrong assumptionsRead every line before accepting
Assuming AI remembersAI loses context after long conversationsRe-state key details every few turns

Prompt engineering for different AI tools

The same structured approach works across every tool in your workflow:

  • OpenCode / Claude Code (CLI agents): State the task and the files to modify. "Add a what's-on events section to products/schoolapp/app-mockup.html after the dashboard. Four event cards with date, title, description, and tag."
  • ChatGPT (chat): Start with context + role. "You are an infrastructure engineer writing PowerShell. Generate a script that exports Intune device compliance policies to CSV."
  • Copilot (inline): Write a clear comment or function name. "// Calculate the number of days until the dissertation deadline" — Copilot completes the rest.
Exercise — Build Something Small

Choose one: (a) a personal bookmark page, (b) a habit tracker for this week, or (c) a simple HTML page for anything you need. Use the four-element prompt structure (context, task, format, constraints). Start with the shell, then add features one prompt at a time. End with a polished output you'd actually use.

Key takeaways

  • Four elements — every prompt needs context, task, format, and constraints
  • Role prompting — tell AI who it is before asking it to build
  • Small pieces — break products into prompt-sized chunks to reduce rework
  • Precise iterations — tell AI exactly what changed, not that something is wrong
  • Delivery Prompt pattern — phase-based prompting scales from one file to a whole product
  • Always review — AI gets faster, not more correct. You are the quality gate.
