Module 4: Branches & Pull Requests

Create branch → Edit → Commit → Push → PR → Review → Merge. Everyone resolves a merge conflict.

Self-paced · ~90 min

Read

What is a branch?

A branch is a parallel version of the repository. Changes on a branch don't affect main until they're merged. This lets you work safely without breaking the stable version.

Never commit directly to main. Always create a branch, make changes, open a PR, get reviewed, and merge.

Think of main as a straight line. A branch diverges from it, commits happen on the branch, then a PR merges it back into main. This mental model makes everything click.

Creating and switching branches

$ git branch add-docs
# Creates a branch called add-docs
$ git switch add-docs
# Switches to the new branch

Shortcut — create and switch in one command: git switch -c add-docs

Pull Requests

A Pull Request proposes changes from a branch to main. It's where review happens.

Every PR should include:

  • Description: What changed, why, and how to test. Reference Issues with #issue-number.
  • Reviewers: At least one person assigned to review.
  • Checks: GitHub Actions runs automatically. All checks must pass before merging.

Reviewers can:

  • Comment on specific lines — ask questions, suggest improvements
  • Approve — changes look good, ready to merge
  • Request changes — something needs fixing before merging

Merge types and conflicts

Three merge types:

  • Merge commit: Preserves all commits from the branch. History shows the branch existed.
  • Squash merge: Combines all branch commits into one. Clean history. Use this for feature branches.
  • Rebase merge: Rewrites commits to appear as if they were made on main sequentially. Advanced.

Merge conflicts: When two branches edit the same line differently. Git marks the conflict in the file:

<<<<<<< HEAD
This is the version on main
=======
This is the version on my branch
>>>>>>> my-branch

You edit the file to keep the correct version, remove the conflict markers, stage, commit, and push.

Conflicts are normal. They're not a mistake. Every engineer resolves conflicts. Read the markers, keep the correct version, and move on.

Try it yourself — Full PR Cycle

Run through the complete cycle on your own practice repo:

  • Create a branch: git switch -c demo-pr
  • Edit a file, stage, commit, push
  • Open a PR on GitHub.com — write a description, check the diff, assign yourself as reviewer
  • Merge the PR (squash merge)
  • Switch to main, pull, verify the changes
  • Create a deliberate conflict: edit a line on main, then try to merge a branch that edits the same line differently — resolve it manually

Exercise — Cross-Team PR

Find a partner or use two GitHub accounts. Create a shared practice repository and add each other as collaborators:

  • You create a branch, edit the team roster file, commit, push, and open a PR
  • Your partner reviews the PR, leaves a comment, approves
  • You merge. Swap roles.
  • Now create a deliberate conflict: both of you edit the same line in the same file on separate branches. Try merging — resolve the conflict together.

Common pitfalls

  • Working on main: Never commit to main directly. Always create a branch first.
  • Vague PR descriptions: "Updated stuff" is not a description. Write what changed and why.
  • Merging your own PR: Always get at least one review. No self-merges to main.
  • Fear of conflicts: Conflict markers just mean you need to decide: keep the left version, the right version, or combine them.
