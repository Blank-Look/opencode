Module 4: Branches & Pull Requests

Create branch → Edit → Commit → Push → PR → Review → Merge. Everyone resolves a merge conflict.

2 h — 30 min instruction + 1.5 h exercise Afternoon Day 1 · 13:30–15:30

Facilitator preparation

  • Ensure the training repo has branch protection disabled (or use a practice repo)
  • Prepare pairs or small groups for the cross-team PR exercise
  • Create a deliberate conflict scenario — a file with the same line editable by two people
  • Have a sample PR open to show the review interface (comment, approve, request changes)
  • Know the three merge types: merge commit, squash merge, rebase merge

Script & talking points

What is a branch? (5 min)

A branch is a parallel version of the repository. Changes on a branch don't affect main until they're merged. This lets you work safely without breaking the stable version.

Never commit directly to main. Always create a branch, make changes, open a PR, get reviewed, and merge.

Whiteboard

Draw main as a straight line. Show a branch diverging, commits happening on it, then a PR merging it back into main. This visual makes everything click.

Creating and switching branches (5 min)

$ git branch add-docs
# Creates a branch called add-docs
$ git switch add-docs
# Switches to the new branch

Shortcut — create and switch in one command: git switch -c add-docs

Pull Requests (10 min)

A Pull Request proposes changes from a branch to main. It's where review happens.

Every PR should include:

  • Description: What changed, why, and how to test. Reference Issues with #issue-number.
  • Reviewers: At least one person assigned to review.
  • Checks: GitHub Actions runs automatically. All checks must pass before merging.

Reviewers can:

  • Comment on specific lines — ask questions, suggest improvements
  • Approve — changes look good, ready to merge
  • Request changes — something needs fixing before merging

Merge types and conflicts (5 min)

Three merge types:

  • Merge commit: Preserves all commits from the branch. History shows the branch existed.
  • Squash merge: Combines all branch commits into one. Clean history. Use this for feature branches.
  • Rebase merge: Rewrites commits to appear as if they were made on main sequentially. Advanced.

Merge conflicts: When two branches edit the same line differently. Git marks the conflict in the file:

<<<<<<< HEAD
This is the version on main
=======
This is the version on my branch
>>>>>>> my-branch

You edit the file to keep the correct version, remove the conflict markers, stage, commit, and push.

Conflict tip

Conflicts are normal. They're not a mistake. Every engineer resolves conflicts. The key is to read the markers, talk to the other person if you're unsure, and keep the correct version.

Live demo (5 min)

Run through the complete cycle:

  • Create a branch: git switch -c demo-pr
  • Edit a file, stage, commit, push
  • Open a PR on GitHub.com — show the description, diff, and reviewer assignment
  • Merge the PR (squash merge)
  • Switch to main, pull, verify the changes
  • Introduce a conflict: have someone else edit the same line on main, then try to merge your branch

Exercise — Cross-Team PR (90 min)

Instructions

Split into pairs. Person A creates a branch, edits the team roster file, commits, pushes, and opens a PR. Person B reviews the PR, leaves a comment, approves. Person A merges. Swap roles.

The facilitator introduces a deliberate conflict: both people edit the same line in the same file. Each pair resolves their conflict together.

Common pitfalls

  • Working on main: Remind constantly — never commit to main directly. Always branch.
  • Vague PR descriptions: "Updated stuff" is not a description. Write what and why.
  • Merging your own PR: Always get at least one review. No self-merges to main.
  • Fear of conflicts: Demystify conflict markers. Show that it's just a decision: keep left, keep right, or combine.
