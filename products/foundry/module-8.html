Module 8: Engineering Standards

Repository naming, PR rules, branch protection, Issues, Projects, documentation. How your team works.

Self-paced · ~25 min

Read

Why standards matter

Standards are not bureaucracy. They're what makes a team efficient. When every repo looks the same, every PR follows the same rules, and every engineer knows where to find things, you spend less time figuring out "how we do things here" and more time doing the actual work.

Your team should document its decisions in an engineering-standards.md file that lives in the team's repository. The sections below cover what you need to decide.

Repository naming conventions

Follow these conventions for consistency:

  • Lowercase with hyphens: intune-packaging, azure-lz-docs
  • Prefix for related groups: entra-id-scripts, entra-id-policies
  • No spaces, no uppercase, no underscores

PR requirements

Set a minimum bar for every Pull Request:

PR checklist

  • Every PR must have a description — what changed and why
  • At least one reviewer must approve
  • All status checks must pass (if Actions are configured)
  • No self-merges to main — someone else merges your PR
  • Use squash merge for feature branches (clean history)

Branch protection

Enable branch protection on main in Settings → Branches → Add rule:

  • Require a pull request before merging
  • Require at least 1 approval
  • Dismiss stale reviews when new commits are pushed
  • Require status checks to pass (once you have workflows)
  • Do not allow bypassing the above settings

Issues and Projects

Issues: Use for tasks, bugs, and enhancements. Common labels:

  • bug — something broken
  • enhancement — new feature or improvement
  • docs — documentation changes
  • question — needs discussion
  • good first issue — for new team members

Projects: Kanban boards with columns: To Do, In Progress, In Review, Done. Link Issues and PRs to cards for a real-time view of work in flight.

Documentation policy

  • Engineering documentation lives in Markdown in the repository, not SharePoint
  • Every repository has a README.md and a docs/ folder
  • Documentation is reviewed through PRs, just like code
  • Repository templates ensure every new repo starts with the standard structure

Exercise — Write Your Team Standards

Create an engineering-standards.md file in your practice repository. Based on what you've read, write down your decisions for:

  • Repository naming conventions
  • PR requirements (checklist)
  • Branch protection rules
  • Issue labels
  • Documentation policy

Commit the file and open a PR. Ask a teammate to review it. This becomes your team's living standards document.
